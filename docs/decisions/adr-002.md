# ADR-002: Gestión de estado con Signals y servicios nativos en lugar de NgRx

## Estado
**Aceptado** - Octubre 2026

> Decisión controversial. Reemplaza el uso de NgRx que venía insinuado en el
> código base del proyecto (se habían declarado `@ngrx/store`, `@ngrx/effects` y
> `@ngrx/store-devtools` en la configuración de la aplicación). Esta decisión
> genera debate porque NgRx es, para muchos equipos Angular, el estándar de facto
> para gestión de estado.

## Contexto

La aplicación **Angular Architecture Docs** renderiza documentación C4 y diagramas
Mermaid. El estado que maneja es acotado: la sección C4 activa, el contenido
Markdown/diagrama cargado, el estado de la navegación (sidenav) y, a lo sumo,
feature flags y preferencias de UI. No hay flujos transaccionales complejos,
colaboración en tiempo real ni grandes grafos de entidades normalizadas.

El código base original configuraba NgRx (`provideStore`, `provideEffects`,
`provideStoreDevtools`) pero sin reducers, acciones ni effects reales: era
andamiaje de una librería de estado global sin estado que gestionar. Durante la
Fase 0 esos proveedores se removieron para que el proyecto compilara. Esto obliga
a tomar una decisión explícita: **¿qué estrategia de gestión de estado adopta el
proyecto de ahora en adelante?**

Angular 20 ofrece Signals como primitiva reactiva de primera clase, lo que cambia
el cálculo de trade-offs respecto a cuando NgRx era prácticamente la única
respuesta madura para estado reactivo.

## Fuerzas

- **Complejidad del dominio**: el estado actual es simple y mayormente local a
  cada vista. No hay evidencia de necesidad de un store global normalizado.
- **Tamaño del bundle**: la app se sirve como estática; cada dependencia pesa en
  el tiempo de carga inicial.
- **Curva de aprendizaje**: NgRx impone un modelo (acciones, reducers, selectors,
  effects) que no todo el equipo domina y que es costoso de mantener bien.
- **Trazabilidad y depuración**: NgRx aporta time-travel debugging y un flujo de
  datos unidireccional explícito, valioso en dominios complejos.
- **Escalabilidad futura**: si el producto creciera hacia edición colaborativa o
  sincronización, un store estructurado podría pagar su costo.
- **Consistencia con el stack**: Signals es nativo de Angular 20 y no agrega
  dependencias ni divergencia conceptual con el framework.
- **Riesgo de sobre-ingeniería**: adoptar NgRx "por si acaso" es un antipatrón
  frecuente que penaliza la velocidad sin beneficio inmediato.

## Opciones evaluadas

### Opción A: Signals + servicios inyectables (elegida)
Estado local con `signal`/`computed` en componentes y servicios `providedIn:
'root'` para estado compartido (p. ej. `DocumentationService`).

**Pros**:
- Cero dependencias adicionales; nativo de Angular 20.
- Curva de aprendizaje baja; alineado con la dirección oficial del framework.
- Menos boilerplate: no hay acciones/reducers/effects para estado trivial.
- Bundle más liviano, relevante para una app estática.

**Contras**:
- Sin time-travel debugging ni DevTools de estado "de fábrica".
- La disciplina de dónde vive cada pieza de estado depende de convenciones del
  equipo, no de la estructura impuesta por una librería.
- Si el dominio crece mucho, puede requerir refactor hacia un patrón más formal.

### Opción B: NgRx (store global)
Store centralizado con acciones, reducers, selectors y effects.

**Pros**:
- Flujo de datos unidireccional explícito y auditable.
- Redux DevTools: time-travel y trazabilidad de cada cambio.
- Patrón conocido y estandarizado para equipos grandes.
- Escala bien ante estado complejo y compartido entre muchas vistas.

**Contras**:
- Boilerplate significativo para un dominio tan simple como el actual.
- Dependencias extra (`store`, `effects`, `store-devtools`) y mayor bundle.
- Curva de aprendizaje y riesgo de implementaciones inconsistentes.
- Sobre-ingeniería evidente dado el estado real que maneja la app hoy.

### Opción C: NgRx SignalStore
Enfoque intermedio: el store de NgRx construido sobre Signals.

**Pros**:
- Menos boilerplate que el NgRx clásico.
- Mantiene una estructura de store reconocible y DevTools.

**Contras**:
- Sigue siendo una dependencia externa para un dominio simple.
- API relativamente nueva; menos material y experiencia acumulada en el equipo.
- Agrega un concepto más a aprender sin resolver un problema que hoy exista.

## Decisión

Se adopta la **Opción A: Signals + servicios inyectables** como estrategia de
gestión de estado del proyecto, y se descarta NgRx para el alcance actual.

Fundamento:
1. El estado real de la aplicación es simple y mayormente local; NgRx sería
   sobre-ingeniería.
2. Signals es nativo de Angular 20, sin costo de dependencias ni divergencia con
   el framework.
3. Se prioriza velocidad de desarrollo y bundle liviano, coherente con una app
   servida de forma estática.
4. La decisión es reversible: si el dominio crece, se puede migrar a NgRx
   (clásico o SignalStore) de forma incremental.

## Consecuencias

### Positivas
- Menos dependencias y bundle más pequeño.
- Menor fricción para nuevas contribuciones; menos conceptos que aprender.
- Código de estado colocalizado con la vista que lo usa, más fácil de seguir para
  cambios pequeños.

### Negativas
- Se pierde el time-travel debugging y las DevTools de estado que ofrece NgRx.
- Sin la estructura impuesta por una librería, el equipo debe acordar y respetar
  convenciones sobre dónde vive el estado compartido.
- Un crecimiento fuerte del dominio podría exigir un refactor futuro.

### Mitigaciones
- Definir una convención clara: estado local en el componente; estado compartido
  en servicios `providedIn: 'root'` expuesto como `signal`/`computed` de solo
  lectura hacia afuera.
- Documentar el flujo de datos en el diagrama de componentes (nivel 3 de C4).
- Revisar esta decisión mediante los disparadores de re-evaluación de abajo antes
  de que el estado se vuelva inmanejable.

## Partes interesadas y su perspectiva

- **Desarrolladores**: ganan simplicidad y velocidad; pierden una red de seguridad
  estructural y herramientas de depuración de estado.
- **Arquitecto**: asume el compromiso de vigilar que el estado no crezca sin
  gobierno y de disparar el refactor a tiempo si hace falta.
- **Negocio**: se beneficia de menor time-to-market y menor costo de
  mantenimiento mientras el dominio siga siendo simple.

## Disparadores de re-evaluación

Esta decisión se revisará si:
- Aparece estado compartido complejo entre muchas vistas o sincronización en
  tiempo real.
- La depuración de estado se vuelve recurrentemente difícil sin DevTools.
- El equipo detecta inconsistencias por falta de una estructura formal de estado.

## Relación con otras decisiones
- **ADR-001** (adopción de Mermaid): ambas decisiones comparten el principio rector
  de **minimizar dependencias y favorecer lo nativo/versionable**. ADR-001 lo
  aplica a diagramas; ADR-002 lo aplica a gestión de estado.
